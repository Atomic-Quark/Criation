The verdict

Not safe to launch — and it cannot currently take payment

Criation is a genuinely impressive front-end: 30 routes, a rich storefront, seller, supplier, dropship, affiliate and admin consoles, invoices, a wallet, coupons and multi-currency. But almost none of it is backed by a server. Orders are created in the browser, stamped paymentStatus: "paid", and saved to localStorage. The card form on checkout has a hard-coded test card in it and sends nothing anywhere. Any registered user can make themselves an administrator by adding one field to the login request, and an unauthenticated GET /api/seed creates an admin account with a published password.

Treat what exists as a high-fidelity prototype of the product. The work ahead is to build the server that the prototype has been miming — auth, authorization, catalog, cart, orders, payments — and then harden it.

What is genuinely good

  • Monorepo hygiene is strong: Turborepo tasks, shared eslint/tsconfig presets, workspace packages, clean env-resolution helper that never throws at import time.
  • TypeScript is strict enough to be useful and everything typechecks across all 10 workspaces.
  • Mongoose schemas for User, Product, Order and Upload are well-modelled with indexes, enums and a toSafeProfile() that correctly strips the password hash.
  • Passwords are hashed with bcrypt — never stored in plain text.
  • The auth cookie is httpOnly, sameSite: lax and secure in production. The right shape, just not yet enforced anywhere.
  • The UI itself is production-quality: dark mode without flash, responsive layout, toasts, skeletons, a real design language.

What is actually wired together

The single most important finding is not a bug — it is the shape of the system. The storefront makes exactly four network calls in the entire codebase: login, register, logout and file upload. Everything else is browser state.

Server-backed localStorage only Dead code

Two backends, neither of them the real one

backend/api is an Express service with an in-memory catalog and a placeholder login that only accepts demo@criation.example. Nothing calls it. The web app instead grew its own Next.js route handlers talking to MongoDB. Those two worlds also disagree on fundamentals: @criation/types stores prices in paise (249900 = ₹2,499) while apps/web/src/types/store.ts stores rupees (399). Any future integration between them silently multiplies or divides every price by 100.

Critical — fix before this is exposed to anyone

C-1

Any user can promote themselves to administrator

apps/web/src/app/api/auth/login/route.ts · apps/web/src/app/api/auth/register/route.ts

Both routes read role straight from the request body. Login writes it onto the user after the password check (user.role = role; if (role === "admin") user.isAdminVerified = true; await user.save()), and register creates the account with whatever role was posted. One curl with "role":"admin" turns any account into a verified superadmin, permanently, in the database.

FixNever accept role from a client. Force role: "customer" on registration and drop the role-switching branch from login entirely. Role changes belong behind an admin-only endpoint with an audit log.

C-2

A public URL creates an admin account with a known password

apps/web/src/app/api/seed/route.ts

The seed route exports both POST and GET, has no authentication, and creates mrdiv@criation.example with role: "admin", isAdminVerified: true and the password admin123. Anyone who opens /api/seed on the deployed site can then log in as an administrator. It can also be hit in a loop to hammer the database.

FixDelete the route from the app. Seeding belongs in a CLI script run against a database by an operator, never in an HTTP handler. If it must stay, gate it on NODE_ENV !== "production" plus a secret header, and remove the GET export.

C-3

The site cannot take payment — orders are marked paid in the browser

apps/web/src/context/StoreContext.tsx · apps/web/src/app/checkout/page.tsx

createOrder() runs entirely client-side: it invents an order number, sets paymentStatus: "paid" and a fake transactionId, waits 1,200 ms on a setTimeout and pushes to the confirmation page. The card form has defaultValue="4532 8910 2341 8912" and CVV 842 baked in and reads them nowhere. The UPI step shows a static QR icon, not a real intent. No gateway, no charge, no webhook, no ledger.

FixSee the Payments section. Nothing about the current checkout is salvageable as a payment path; the UI can stay, the flow underneath must be rebuilt server-first.

C-4

The JWT signing secret is published in the source tree

apps/web/src/lib/auth/jwt.ts · apps/web/.env.example · .env.example

process.env.JWT_SECRET || "criation_jwt_master_secret_key_2026_artisan_dropship_platform_v2" — the fallback is a real, working secret, and the identical value sits in apps/web/.env.example, which is currently untracked but not git-ignored, so the next git add . commits it. Anyone with the repository can forge a valid admin token for any deployment that forgot to set the variable.

FixThrow at boot when JWT_SECRET is missing (requireEnv() already exists in @criation/config). Rotate the secret, replace both example files with a placeholder, and add a secret-scanning hook.

C-5

Admin, seller and supplier consoles have no server-side authorization

apps/web/src/app/admin/page.tsx · StoreContext.authenticateAdmin · no middleware.ts

There is no middleware.ts anywhere in the repo, and no route handler ever checks a role. /admin, /seller, /supplier and /dropship are statically prerendered pages gated by React state. authenticateAdmin() accepts the literal strings admin123, superadmin, criation_admin, demo or admin — and the failure toast helpfully says "Try 'admin123'". Editing criation_user_v1 in devtools is equally effective.

FixAdd middleware.ts that verifies the JWT and role for every /admin, /seller, /supplier and privileged /api path, plus a per-handler requireRole() check. Delete the master-key mechanism.

C-6

Write endpoints are unauthenticated and mass-assign the request body

apps/web/src/app/api/products/route.ts · apps/web/src/app/api/orders/route.ts

Product.create({...body}) and Order.create({...body, date}) spread unvalidated client JSON into Mongoose. No auth, no schema validation. A stranger can insert catalog entries, or insert orders with total: 1 and paymentStatus: "paid". Notably @criation/validation already contains Zod schemas for exactly these shapes — they are simply not used by the web app.

FixRequire an authenticated session and the right role, parse the body with the existing Zod schemas, and allowlist fields explicitly. Money fields must be computed server-side and never accepted from a client.

C-7

Anonymous file upload with no type, size or quota limit

apps/web/src/app/api/storage/upload/route.ts

Anyone can POST any file of any size and it is written to public/uploads and served from your origin. There is no session check, no MIME allowlist, no byte cap and no rate limit. An .html or .svg upload becomes stored XSS on your own domain (same-origin, so it can read the auth cookie's effects); a large loop fills the disk. It is also a plain multipart POST, which means it is CSRF-able even with sameSite: lax.

FixRequire auth, allowlist image/jpeg|png|webp|avif, verify the magic bytes rather than trusting file.type, cap at a few MB, re-encode through sharp, and store on S3/Cloudinary behind a CDN — not in public/.

C-8

A database outage becomes an authentication bypass

apps/web/src/app/api/auth/login/route.ts (catch block) · api/auth/me

When MongoDB is unreachable, login falls into a catch block that accepts any of five demo addresses — including admin@criation.example — with the password password123 or admin123, and issues a real signed JWT with whatever role the body asked for. /api/auth/me has the same pattern: on a DB error it returns a successful session built from the token alone. An attacker who can degrade your database (or simply catch a real outage) gets admin.

FixDelete every fallback branch. A datastore failure must return 503, never a credential. Same for the mock-catalog fallbacks in the product and order routes — serving fixtures as if they were real data hides outages from your monitoring too.

High

H-1

Identity is read from localStorage and never verified against the server

apps/web/src/context/StoreContext.tsx

The auth cookie is set correctly, but nothing ever validates it after login — /api/auth/me is never fetched. On every page load the entire user object, including role, isAdminVerified and walletBalance, is rehydrated from criation_user_v1, which the user controls.

FixRestore the session server-side on request (a server component or /api/auth/me call on mount), and treat localStorage as a cache of non-authoritative UI state only.

H-2

Every first-time visitor arrives already signed in as a named user

apps/web/src/lib/data/mockCatalog.ts → initialUserProfile

The default store state is isAuthenticated: true for "Divyanshu Sharma" with a ₹750 wallet, 350 loyalty points, a Gurugram address and a Gold tier. A brand new visitor sees someone else's name, address and balance, and can check out without ever creating an account.

FixDefault to a genuine guest: no name, no wallet, isAuthenticated: false. Keep the demo profile behind a seed script.

H-3

Order history exists only in the customer's browser

apps/web/src/context/StoreContext.tsx → createOrder / STORAGE_KEYS.ORDERS

Orders are never sent to /api/orders. Clearing site data, switching device or opening a private window destroys every order. You have no server record to fulfil, refund, dispute or account for — and no way to answer a customer asking where their parcel is.

FixMake order creation a server operation that returns the persisted order; the client should only ever render what the server confirmed.

H-4

The wallet is free money and coupons are validated client-side

StoreContext → addWalletMoney, applyCoupon, cancelOrder

addWalletMoney(amount) credits the balance with no payment step at all. Cancelling a "paid" order refunds the full total into the wallet. Coupon codes are matched against a client-side array, so discount rules, minimum-order values and expiry are all editable by the customer. Totals, GST and shipping are likewise computed in the browser.

FixMove pricing, coupon validation and every wallet mutation server-side into a ledger with immutable entries. The client sends item IDs and quantities; the server returns the price.

H-5

No security response headers at all

apps/web/next.config.ts

No headers() block: no Content-Security-Policy, HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy or Permissions-Policy. The site can be framed for clickjacking, and there is no CSP backstop against injected script.

FixAdd a headers() block with a nonce-based CSP, Strict-Transport-Security: max-age=63072000; includeSubDomains; preload, frame-ancestors 'none', nosniff and Referrer-Policy: strict-origin-when-cross-origin.

H-6

The image optimizer is an open proxy

apps/web/next.config.ts → images.remotePatterns

{ protocol: "https", hostname: "**" } lets anyone pass any URL through /_next/image. That turns your server into a bandwidth relay and an SSRF-adjacent fetcher, billed to you.

FixReplace the wildcard with the explicit hosts you serve from (your CDN, Cloudinary, Unsplash) and set images.dangerouslyAllowSVG: false.

H-7

No rate limiting, lockout or bot protection anywhere

all route handlers

Login, register, upload and seed can each be called without limit. Credential stuffing, mass account creation and disk-filling uploads are all unimpeded, and there is no CAPTCHA or device check on any sensitive action.

FixPer-IP and per-account rate limits (Upstash Redis or your host's WAF), exponential lockout after failed logins, and a bot check on registration and password reset.

H-8

No password policy, no verification, no password reset

apps/web/src/app/api/auth/register/route.ts

Registration accepts a one-character password. Email and phone are never verified, so accounts can be created against addresses the user does not own. There is no forgot-password flow at all — a customer who forgets their password is permanently locked out, and support has no recovery path.

FixMinimum 8–12 characters with a breach check (Have I Been Pwned k-anonymity API), email verification before first order, and a token-based reset flow with short expiry and single use.

H-9

Uploads to the local filesystem will not work in production

apps/web/src/app/api/storage/upload/route.ts

The route writes to process.cwd()/public/uploads. On Vercel, Netlify or any container that redeploys, that directory is read-only or ephemeral — uploads either throw or vanish on the next deploy, and never appear on other instances.

FixUpload to object storage (S3 + CloudFront, Cloudinary, or UploadThing) using presigned URLs so the file never transits your server.

H-10

16 dependency advisories, 5 rated high

npm audit

Almost all of them come through the Expo toolchain in apps/mobile (@expo/config-plugins and friends). Build-time only today, but they gate any clean CI pipeline.

FixRun npm audit fix, bump Expo to a patched SDK, and add npm audit --omit=dev to CI as a blocking step.

Medium

M-1

234 lint errors block any quality gate

apps/web — turbo run lint exits 1

Mostly unused imports and any in the new storefront code, plus a few unescaped entities. Until this is clean you cannot make lint a merge requirement, which is how the rest of the list stays fixed.

Fixnpm run lint:fix, then type the remaining catch (e: any) blocks as unknown and narrow.

M-2

Zero tests and no CI pipeline

repository root

No test files exist and there is no .github/workflows. Nothing prevents a regression in pricing, auth or checkout from reaching production.

FixVitest for pricing/coupon/tax logic and every auth handler, Playwright for the browse → cart → checkout → order journey, and a GitHub Actions workflow running lint, typecheck, test, build and audit on every PR.

M-3

Two backends and two type systems that disagree

backend/api vs apps/web/src/app/api · @criation/types vs apps/web/src/types/store.ts

The Express service is unreachable dead weight; the shared packages (api, ui, validation, types) are used by admin and mobile but not by the app that matters. Prices are paise in one and rupees in the other.

FixDecide on one home for business logic — Next route handlers, or the Express service — and delete or fully adopt the other. Standardise on integer minor units (paise) everywhere and format at the edge.

M-4

No inventory control, and order numbers collide

StoreContext → createOrder

Stock is never decremented, so the same item can be sold indefinitely. Order IDs are CR- plus four random digits — roughly a 1-in-10,000 collision per order, and the number is generated on the client where two customers can produce the same one.

FixServer-generated order numbers from a sequence or ULID, and an atomic stock decrement in the same transaction as order creation.

M-5

GST is a flat 5% and the invoice is not a compliant tax invoice

StoreContext → cartTax · lib/invoice/generateInvoice.ts

Every product is taxed at 5% regardless of HSN classification, and the generated document calls itself a Tax Invoice while carrying no GSTIN, no HSN/SAC codes, no place-of-supply and no IGST-versus-CGST/SGST split. For an Indian marketplace selling across states, that is a compliance problem, not a formatting one.

FixPer-product HSN and GST rate on the product model, place-of-supply logic driving CGST+SGST versus IGST, seller GSTIN on the invoice, and sequential invoice numbering per financial year.

M-6

The AI concierge and AI tools are keyword matching

apps/web/src/components/ai/AIChatWidget.tsx · app/ai-tools/page.tsx

The widget is a chain of if (q.includes("gift")) branches behind a 700 ms fake typing delay. That is fine as a demo, but it is presented to users as an AI assistant, and it will fail on the first real question.

FixEither wire it to a real model through a server route (never expose an API key to the browser), with a strict system prompt, rate limiting and a cost cap — or relabel it as a guided help menu.

M-7

Legal pages claim compliance the platform does not have

apps/web/src/app/legal/[slug]/page.tsx

The privacy policy states that transactions run through "256-bit SSL encrypted, PCI-DSS Level 1 compliant payment gateways". There is no gateway. Checkout repeats the claim. Publishing that to real customers is a consumer-protection exposure independent of the technical one.

FixRewrite the legal pages against what the platform actually does once payments are live, and have them reviewed. Add the disclosures Indian e-commerce rules require: seller identity, grievance officer, return window, shipping timelines.

M-8

No transactional email or SMS

whole app

Nothing is ever sent to a customer: no order confirmation, no shipping notification, no OTP, no password reset, no invoice delivery. Notifications exist only as in-app toasts stored in the browser.

FixAdd a transactional provider (Resend, SES or Postmark; MSG91 for Indian SMS) driven by server-side order events, with templates and delivery logging.

M-9

Product and order pages are client-only — no SSR, no SEO surface

app/products/[id]/page.tsx · app/orders/[id]/page.tsx · no sitemap or robots

Every product page is "use client" reading from context, so there is no per-product <title>, description, canonical URL, Open Graph image or Product structured data — and no sitemap.ts or robots.ts. For a storefront that lives on search traffic, this is the difference between existing and not existing on Google.

FixConvert product and category pages to server components with generateMetadata(), add JSON-LD Product/Offer/BreadcrumbList, and add sitemap.ts, robots.ts and a web manifest.

M-10

Currency conversion uses hardcoded rates

StoreContext → CURRENCY_RATES

USD, EUR and GBP prices are computed from constants written into the bundle. They were wrong the day after they were written, and a customer can be charged a different amount than they were shown.

FixEither sell in INR only and display a clearly-labelled indicative conversion, or fetch daily rates server-side and freeze the rate onto the order at capture time.

M-11

Silent database fallbacks hide outages

lib/db/mongodb.ts and every route's catch block

A failed connection logs a warning and the route returns mock catalog data with success: true. Monitoring sees healthy 200s while the database is down, and customers browse a fictional catalog. The connect handler also logs part of the connection string.

FixFail loudly — return 503, emit a structured error to Sentry, and add a real health check. Remove the URI from the log line.

Getting to real payments

The product is priced in INR with UPI, cards, netbanking, wallet and COD — so the natural choice is an Indian gateway: Razorpay or Cashfree (both cover UPI intent and collect, cards with RBI-compliant tokenisation, netbanking, COD reconciliation and marketplace-style split settlements). Add Stripe only if you sell outside India. The gateway matters less than the shape of the flow.

The flow that has to replace the current one

StepWhere it runsWhat happens
Cart pricedServerClient sends product IDs + quantities only. Server looks up prices, applies coupons it validated itself, computes GST and shipping, returns the total.
Order draftedServerAn order row is written with status pending and the server-computed amount. It is never paid at this point.
Gateway order createdServerCall the gateway with that amount and your order ID as the receipt. Keys stay server-side; only the returned order token reaches the browser.
Customer paysGateway's UITheir hosted checkout or SDK collects the card or UPI. Your card form is deleted — no PAN or CVV ever touches your code.
Webhook confirmsServerThe gateway calls your webhook. Verify the HMAC signature, check the amount matches your order, then and only then mark it paid. Make it idempotent — webhooks retry.
Fulfilment startsServerDecrement stock in the same transaction, send the confirmation email, generate the invoice, create the shipment.
ReconcileServer, dailyCompare gateway settlements against your order ledger and alert on any mismatch.

Rules that are not optional

  • Never trust a client-reported payment. The browser's success callback is a UI hint. Only a signature-verified webhook (or a server-side status fetch) may change an order to paid.
  • Never store card data. Delete the card fields from checkout entirely. Using a hosted gateway UI keeps you in PCI SAQ-A, the lightest tier. RBI rules also prohibit merchants storing card numbers — tokenisation is the gateway's job.
  • Amounts are integers in paise, server-side, always. Never take a total from the request body.
  • Idempotency keys on every charge and refund, so a retried request cannot double-charge.
  • COD needs its own path: no capture at checkout, a confirmation call or OTP to suppress fake orders, and remittance reconciliation from the courier.
  • Subscriptions need a mandate, not a stored card — UPI Autopay or e-NACH, with dunning and clear cancellation.
  • Refunds are a first-class flow: partial and full, tied to the return workflow, reflected in the invoice and the ledger.

What you need before you can go live commercially

  • A registered business entity, PAN, GSTIN and a current account for gateway KYC.
  • Published policies the gateway will check: refund, shipping, terms, privacy, contact — the current placeholder copy will not pass, and it currently claims certifications you do not hold.
  • A live domain on HTTPS with the storefront actually working, since gateways review the site during onboarding.
  • A grievance officer and contact details published, per Indian e-commerce rules.

Security hardening checklist

Work top-left to bottom-right. The first group is what stops the current attacks; the rest is what keeps it stopped.

Authentication
  • Reject role from any client input
  • Fail boot on a missing JWT_SECRET; rotate the leaked one
  • Delete every DB-failure auth fallback
  • Short-lived access token + rotating refresh token
  • Server-side session revocation on logout and password change
  • Password minimum length + breach check
  • Email verification and a real reset flow
  • Lockout and exponential backoff on failed logins
  • bcrypt cost 12, or move to argon2id
Authorization
  • middleware.ts guarding /admin, /seller, /supplier
  • requireRole() inside every privileged handler
  • Ownership checks — a user may only read their own orders
  • Delete the hardcoded master-key mechanism
  • Audit log for every admin action
Input & data
  • Zod validation on every route (schemas already exist)
  • Explicit field allowlists — no {...body} into Mongoose
  • Escape user input used in $regex queries
  • Money and tax computed server-side only
  • Cap request body size
  • Sanitise anything rendered as HTML in invoices
Transport & headers
  • Nonce-based Content-Security-Policy
  • HSTS with preload
  • frame-ancestors 'none'
  • X-Content-Type-Options: nosniff
  • Referrer-Policy: strict-origin-when-cross-origin
  • Restrictive Permissions-Policy
  • HTTPS everywhere, HTTP redirected
Abuse & availability
  • Rate limits per IP and per account
  • Bot check on register, login and reset
  • WAF / DDoS protection (Cloudflare or host-native)
  • Upload quotas and virus scanning
  • Timeouts and circuit breakers on outbound calls
  • CSRF tokens on any non-JSON mutating endpoint
Secrets & supply chain
  • Secrets only in the host's secret manager
  • Separate credentials per environment
  • Secret scanning in pre-commit and CI
  • npm audit blocking in CI
  • Dependabot or Renovate enabled
  • Lockfile committed and CI installs with npm ci
Data protection
  • MongoDB Atlas with IP allowlist and TLS, never a public instance
  • Encryption at rest, automated backups, a tested restore
  • Least-privilege database user
  • PII minimisation and a retention policy
  • Export and deletion on request (DPDP Act)
  • No PII, tokens or card data in logs
Operations
  • Sentry for errors, structured request logging
  • Uptime and payment-success-rate alerting
  • Staging environment mirroring production
  • Documented incident response and rollback
  • Penetration test before public launch
  • A published security contact / disclosure policy

The route to launch

Five phases, in dependency order. The estimates assume one or two developers and are calendar time, not effort. Phase 0 is the only one with a hard deadline: it must be done before this code is reachable from the internet at all.

PHASE 0

Close the open doors

1–2 days · blocking
  • Delete /api/seed and move seeding to a script.
  • Strip role from the login and register request bodies.
  • Remove every DB-failure fallback from the auth, product and order routes.
  • Require JWT_SECRET at boot, rotate it, and replace the value in both .env.example files with a placeholder.
  • Lock down the upload route: auth, MIME allowlist, size cap — or disable it until Phase 3.
  • Narrow images.remotePatterns and add the security headers block.
  • Add middleware.ts so privileged routes are not reachable without a verified role.
  • Scrub the secret from apps/web/.env.example, then commit the storefront.
PHASE 1

Move the truth to the server

3–5 weeks
  • Pick one backend — Next route handlers or the Express service — and delete the other.
  • Real sessions: refresh-token rotation, server-side revocation, /api/auth/me actually used on load.
  • Password reset, email verification, rate limiting, lockout.
  • Server-owned catalog, cart, coupons and pricing. The browser stops being the source of truth.
  • Persisted orders with a proper state machine and ownership checks.
  • Standardise on paise across the monorepo; retire the duplicate type system.
  • Vitest on pricing and auth, Playwright on the purchase journey, GitHub Actions running lint, typecheck, test, build, audit.
PHASE 2

Payments

2–3 weeks after Phase 1
  • Gateway account and KYC (start early — approval takes days, sometimes weeks).
  • Server-side order creation, hosted checkout, signature-verified idempotent webhooks.
